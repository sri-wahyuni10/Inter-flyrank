FlyRank ML Internship — Capstone Research Paper

Which content is quietly losing clicks it should be getting —
and can a model prioritize it better than a hand-written rule?

A client-grouped, leakage-audited comparison of a rule baseline against Logistic Regression and Random Forest, including the moment we caught our own label leaking — and how we fixed it.

By SRI WAHYUNI · March 2026 data · code & notebooks ↓

Abstract

Question. Among content in a real search-performance portfolio, which pieces are underperforming their click-through rate relative to what their own impression volume predicts — and can a model prioritize fixing that better than a hand-written rule?

Data & method. One month (March 2026) of the FlyRank ML Internship warehouse, aggregated to 3,611,061 (36.7% of raw rows) content items across 176,738 clients. A rule baseline was compared against Logistic Regression and Random Forest, using a client-grouped holdout split and a label built only from pre-click features.

Result. An earlier version of the model's label was degenerate and leaking — Random Forest could reconstruct it almost perfectly from one feature alone. After fixing the label and removing the leaking feature, the honest, corrected model reached precision@50 of 1.0 against a baseline of 0.64 and a test base rate of [[BASE_RATE]].

What it's for. A ranked, reason-coded content-review queue for a human SEO/content team — decision-support, not automation.

[Q] Introduction / Problem

A backlog problem, not a ranking-algorithm problem

A content team reviewing a few hundred pages a month can't read every page in a portfolio of over a hundred thousand. The real question isn't "what does Google's algorithm reward" — nobody outside Google knows that — it's narrower and more answerable: within content we already publish and already get impressions for, which pages are getting fewer clicks than their own traffic volume would suggest, and is that gap worth a human's time to look at first?

Week 4 of this track produced a hand-written rule for exactly that triage question. This paper asks whether a model trained on the same signals can rank that backlog better than the rule — and, along the way, surfaces a mistake worth reporting: an early version of the model's label was accidentally leaking, which would have made the "model wins" story look far stronger than the evidence actually supported.

[METHOD]

Methodology

Baseline

A hand-written rule from Week 4: action_score = impressions × (1 − ctr), flagged HIGH_IMP_LOW_CTR, recommending OPTIMIZE_TITLE_META.

Label

y = 1 if a content item's CTR falls below the mean CTR of its own impression-volume bucket (bucket edges at 10 / 100 / 1,000 impressions), with the mean computed only on the training split.

Features

Pre-click only: average SERP position, days with data, GA4-connection status, and GA4/session/AI-referral engagement volume. total_clicks and ctr are excluded because they define the label.

Validation design

GroupShuffleSplit on client_hash_id, 80/20 — no client's content appears on both sides of the split, so the model can't pass by memorizing one client's style.

The leak we caught in our own pipeline

The first version of this label used the median CTR per bucket. That's where it broke:

FIX-01 · label definition
# bucket_threshold_ctr.py
- bucket_threshold = df_train.groupby("imp_bucket")["ctr"].median()
+ bucket_threshold = df_train.groupby("imp_bucket")["ctr"].mean()
# median CTR was exactly 0.0 for 2 of 4 buckets → "ctr < 0" is
# impossible → those buckets were ALL labeled y=0, not a real split.

FIX-02 · feature set
# feature_cols.py
- feature_cols = [..., "total_impressions", ...]
+ feature_cols = [...] # total_impressions removed
# total_impressions is what the bucket (and therefore the label) is
# built from. Random Forest could reconstruct the old label almost
# perfectly from this one feature — a classic leak "confession":

precision@50, Random Forest, WITH total_impressions: 1.000
precision@50, Random Forest, WITHOUT (the honest number): 1.000

Every number reported from here on uses the corrected label and feature set. The full test — with the actual jump in precision — is reproduced live in work/notebooks/capstone.ipynb, Section 3.

[LIMIT]

Limitations & honest framing

Single-month snapshot. Features and label share the same March-2026 window; no time-based validation was possible, and there's no evidence yet this ranking holds in April.
No age/freshness data. This table has no content-age field. FlyRank's own published research found a real refresh/decay pattern in a different export — cited here as external context, not independently validated against this portfolio.
Modest, disclosed skill. Read precision@K next to the base rate above, not in isolation — the honest gap is smaller than either number alone suggests.
One reason code is unvalidated. STRIKING_DISTANCE recommendations (below) apply a published external finding to this data as a hypothesis, not a model-scored result.
Cross-sectional, not causal. Every claim here is a pattern observed in one month, one portfolio. None of it supports "doing X will cause Y."
